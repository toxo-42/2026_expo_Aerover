## 2. 마커 사양 — 왜 이 값인가

### 딕셔너리: `DICT_4X4_50`

이미 인쇄 파일 · `align.py` 가 이것이다. 50개 중 8개만 쓰니 ID 간 거리가 넉넉해 오검출이 적다.
(예전 주석의 `Drone/run_mapping.py` 는 저장소에 없다 — 이제 이 폴더가 기준이다.)

### 크기: 한 변 6cm (2026-09-22 확정, 09-29 5cm 실물 시험으로 재확인)

제약은 **드론 카메라 1280×960** 이다. 갠트리 궤도(반지름 1.055m, 높이 1.114m)에서
판 중심을 조준할 때:

```
가까운 쪽 마커  거리 1.23m → 약 69 px    ✅
먼 쪽 마커      거리 1.94m → 약 44 px    ⚠ 아래 표의 검출 한계(40px) 근처 (비스듬히 보여 실제 폭은 더 좁다)
```

9/7 에 만든 PDF 로 잰 검출 시험 (블러 σ=1.8 + 노이즈):

| 마커 화면 크기 | 검출 | 코너 오차 → 실측 환산 |
|---:|:---:|---:|
| 107 px | ✅ | 1.4mm |
| 86 px | ✅ | 2.3mm |
| 53 px | ✅ | 2.8mm |
| 40 px | ✅ | 5.0mm |
| 30 px | ❌ 미검출 | — |

처음엔 여유 있는 10cm 로 시작했지만 디오라마에 비해 커서 실물로 줄여 봤다 (`README.md` "마커 크기"):

- 흐림(σ 1.8 ≈ 실제 드론 카메라) 합성 시뮬레이션: **6cm 최소 4개 · 95% 0.8mm**, 5cm 는 가끔 크게 튄다(95% 17mm)
- 손 촬영 한 바퀴 `size_check`: 10cm · 6cm 둘 다 2개 미만 0% · 자세 실패 0장, 대상 좌표 중앙 6mm (6cm)

먼 쪽 마커 하나하나는 한계에 가깝지만 자세는 보이는 마커 전부로 한 번에 푸니 버틴다 — **6cm 로 간다.**

#### 5cm 실물 시험 — 불합격 (2026-09-29)

디오라마에서 덜 튀게 하려고 같은 판 · 같은 자리에서 6cm 를 5cm 로 바꿔 손 촬영 한 바퀴를 비교했다.
배치표는 각자 가까이 찍은 회차로 쟀다 (6cm 192110 · 5cm 211820, 둘 다 재투영 0.5~0.65px).

| `size_check` | 6cm (194931) | 5cm 낮게 (211321) | 5cm 높게 (212559) |
|---|---:|---:|---:|
| 카메라 높이 / 판 중심 거리 | 0.81 / 1.74m | 0.72 / 1.72m | 0.97 / 1.95m |
| 마커 화면 크기 중앙 | 43px | 35px | 31px |
| 2개 미만 장 | 10% | 25% | 24% |
| 자세 실패 | 5 / 50장 | 15 / 60장 | 12 / 50장 |
| 대상 좌표 중앙 / 95% | **3.3 / 22mm** | 10.1 / 57mm | 5.0 / 48mm |

**촬영 탓이 아니다.** 자세가 확실한 장에서 화면 안 마커를 투영 크기별로 나눠 검출률을 보면(`compare_sessions.py` 와 같은 검출),
5cm 회차가 오히려 선명해서(선명도 2128 · 2230 vs 1164) 같은 px 에서는 더 잘 잡혔다 — 25~30px 에서 6cm 7% · 5cm 57~66%.
그런데도 진 이유는 **25px 미만으로 찍히는 마커 비율**이다 (6cm 37% · 5cm 59~62%). 즉 순수하게 크기 문제이고,
덜 선명하게 찍힌 6cm 가 더 선명한 5cm 를 이겼다. 실제 갠트리(높이 1.1m · 거리 1.5m · 흔들림 없음)에서는
마커가 더 크게 찍히겠지만 차이가 커서 6cm 를 뒤집기는 어렵다고 본다.

### 인쇄 시 주의 — 여기서 망치는 경우가 많다

1. **배율 100% / 등배.** "페이지에 맞춤" 을 끈다. 1쪽 100mm 눈금자로 확인.
2. **인쇄 후 한 변을 자로 잰다.** 6cm 가 아니면 **그 잰 값을 쓴다** (예: 5.9cm). 크기가 틀리면 축척이 통째로 틀어진다.
3. **무광 용지.** 광택지 + 조명 = 반사로 검출 실패.
4. **마커 둘레 흰 여백 2cm 이상.** 검은 테두리 바깥의 밝은 영역으로 경계를 잡는다. 판이 잔디색이라 여백이 없으면 더 나빠진다.
5. **폼보드에 붙여 평평하게.** 종이가 말리면 코너가 밀린다.

## 3. 마커 배치 — 모서리 4 + 변 중앙 4 + 왼 변 보강 2 + 오른 변 보강 2

### 왜 8개인가

드론이 판 중심을 조준해도 1.2m 판 전체가 한 화면에 안 들어온다. 원궤도 360프레임 시뮬레이션:

| 배치 | 한 프레임에 보이는 최소 | 평균 | 2개 미만 프레임 |
|---|---:|---:|---:|
| 모서리 4 | 1 | 1.6 | 43% |
| **모서리 4 + 변 중앙 4** | **4** | **5.0** | **0%** |

실시간 solvePnP 는 마커 1개로도 풀리지만 각도가 튄다. 늘 4개 이상이면 안정적이다.
(3D 맵 정합만 보면 모서리 4개로 충분하다 — 8개는 **실시간 쪽** 때문이다.)

### 건물을 올린 뒤 — 8 · 9 추가 (2026-09-23)

위 표는 판이 비어 있을 때다. 건물 두 동(판 뒤쪽 가장자리, 왼쪽 동 x 0.18~0.52 · 오른쪽 동 x 0.78~1.12,
y 1.00~1.25)을 올리고 갠트리 궤도를 다시 돌리니(`aerover/tools/visibility.py`, 메시 가림 포함)
**드론이 건물 바로 뒤(궤도 70~110°)를 지날 때 마커가 1~2개만 보인다.** 80~88° 에서는 1개라 자세를 못 푼다.
그 자리에서는 판 대부분이 건물에 가리고 **왼쪽 동 왼편 틈으로 판 왼쪽 가장자리 앞부분만** 보인다.
그래서 보강 마커는 판 중앙이 아니라 **왼 변(0번 ↔ 7번 사이)** 에 둔다.

| 배치 | 최소 | 평균 | 3개 미만 구간 |
|---|---:|---:|---:|
| 8개 (지금) | 1 | 4.1 | 14곳 |
| 8개 + 8번 | 2 | 4.7 | 3곳 (80~88°) |
| **8개 + 8번 + 9번** | **3** | **5.5** | **0곳** |

이 수치는 **상한**이다 (흐림 · 조명 · 마커 옆 소품의 가림은 안 넣었다). 붙인 뒤 실물로 `size_check` 확인.
근거 · 명령은 `README.md` "추가 마커 2개".

### 실물 한 바퀴로 본 약한 구간 — 오른 변 11 · 12 추가 (2026-10-03)

### 붙인 뒤에는 떼지 않는다

3D 맵을 만들 때와 시연 때 **같은 자리의 같은 마커**를 봐야 좌표계가 맞물린다.

**배치를 다시 쟀으면 3D 맵 정합(`to_W.json`)도 그 뒤에 찍은 ODM 으로 다시 만든다.**

## 4. 좌표계 정의

```
원점 (0,0,0) = 판 윗면의 앞-왼 모서리   (ID 0 옆)
+X           = 앞 변을 따라 오른쪽
+Y           = 왼 변을 따라 뒤(모니터) 쪽
+Z           = 판 윗면에서 위로
단위         = 미터. 측정은 mm, 기록은 m
```

- 반대편 모서리가 `(1.22, 1.22, 0)`, 판 중심이 `(0.61, 0.61, 0)`, 갠트리 회전축이 그 위다.
- 판 윗면이 Z=0 이다. 바닥(땅)은 Z = -0.600.
- **원점 모서리에 테이프로 표시하고 사진을 남긴다.** "어느 모서리였지?" 가 되면 답이 없다.

## 5. 배치 측정 — 자 대신 사진으로 (2026-09-22 결정)

마커 8개의 위치를 자로 재지 않는다. **마커를 붙인 채 한 바퀴 돌며 찍은 사진**에서 `marker_map.py` 가
마커끼리의 상대 위치를 푼다 (같이 찍힌 마커를 사슬로 잇고, 모든 장을 한꺼번에 번들 조정).
사람이 잴 것은 **인쇄된 마커 한 변 하나**뿐이다 — 이것이 유일한 축척 정보다.

```bash
cd apps/aruco
uv run python marker_map.py ../aerover/sessions/<회차> --size <한 변 실측, m> --ref 0 2 <줄자 m> --inset <m>   # → markers_W.json
uv run python marker_map.py ../aerover/sessions/<회차> --size 0.06 --ref 0 2 1.157 --inset 0.0315 --init markers_W.json   # 다시 붙였을 때
uv run python pose.py ../aerover/sessions/<회차>                                   # 확인: 재투영 ~1px
```

09-29 판의 실제 명령은 둘째 줄이다 (`--inset 0.0315` = 판 가장자리 → 마커 중심 3.15cm).
**결과 파일을 바로 `markers_W.json` 에 쓰지 말고 `--out` 으로 따로 받아** 확인한 뒤 바꾼다 — 앱이 그 파일을 쓴다.

### 찍는 법

- **가까이 · 위에서 50장 안팎** — 마커가 화면에서 40~60px 이상. 판 전체를 한 장에 넣으려고 멀리 찍으면(35px 안팎) 안 풀린다.
- **사진마다 마커 3개 이상.** 마커를 잇는 것은 "같이 찍힌 장" 이다. 2개 미만인 장은 버려진다.
  09-29 에 뒤쪽 변을 마커 2개짜리 장으로만 이으니 5 · 6번이 엉뚱한 자리로 풀렸다 (182957).
  **판을 가로질러 앞 · 뒤 마커가 한 장에 들어오는 사선 샷**을 방향마다 몇 장씩 넣는다. 건물이 가리면 치우고 잰다.
- 여러 방향에서 — 한 방향에서만 보면 깊이 방향 오차가 안 풀린다.
- 흔들리지 않게 — 천천히 돌린다.
- 궤도 한 바퀴(멀리)는 배치 측정용이 아니라 **검증용**이다 (`pose.py` · `size_check.py` · `compare_sessions.py`).

### 사진만으로 안 풀릴 때 — `--init`

`marker_map` 은 마커를 하나씩 풀어(IPPE) 같이 찍힌 마커끼리 사슬로 잇는 초기값에서 번들 조정을 시작한다.
작은 마커를 비스듬히 보면 **평면 뒤집힘 모호성**으로 두 해가 재투영으로 거의 구별되지 않는데, 예전엔 첫 해만 써서
초기값이 자주 갇혔다 (09-29 회차들: 재투영 중앙 3~5px · 최대 20~100px, 판이 찌그러짐). 지금은 **그 장의 판 법선에
가장 많이 모이는 해**를 고른다 → 같은 사진이 0.5~0.75px 로 풀렸다.

그래도 마커가 40px 안팎이고 한 장에 2개씩만 이어지는 회차는 가끔 갇힌다 (220336: 4.9px · 최대 100px).
**이전 배치표가 있으면 `--init markers_W.json` 으로 거기서 출발**시킨다 (220336: 0.67px). 마커를 조금 옮겨 다시 붙인
정도(1cm 안팎)면 충분히 가까운 출발점이다.

**갇혔는지 알아보는 법**: 재투영 중앙이 1px 을 넘거나, 이웃 간격이 줄자와 수 cm 다르거나, 판 한쪽 변 마커만 재투영이
유독 크면(5~35px) 갇힌 것이다. 오검출(판에 없는 ID)은 `--ids` (ID 목록, 기본 `BOARD_IDS` = 0~9 · 11 · 12) 가 걸러 낸다 — 09-29 에 ID 10 · 17 이 잡혀
원점을 끌고 가 배치 전체가 Y 3m 대로 밀린 적이 있다.

### 정확도

| 항목 | 값 | 근거 |
|---|---|---|
| 마커끼리 상대 위치 | 코너 잔차 최대 **0.26mm** | 합성 시험 (`test_marker_map.py`, 30장, 블러 σ1.2) |
| 실물 회차 간 일치 | 코너 차이 중앙 **1.7mm** · 최대 8mm (장수 적은 6번) | 09-29 가까이 찍은 190605 ↔ 192110 |
| 축척 | 마커 한 변 실측 오차와 **같은 비율** | 한 변 0.5mm 틀리면 0.5% → 1.2m 판에서 6mm |

→ 자로 8개를 두 번씩 재던 것보다 정확하고, 붙인 배치가 표와 달라도 상관없다.
**그래서 한 변만은 정성껏 잰다** — 10칸 눈금을 한 번에 대고, 두 번 재서 맞춘다.

### 결과 읽는 법

`marker_map.py` 출력의 "찍힌 장" 이 3 미만인 마커에는 ⚠ 가 붙는다 — 위치를 믿기 어렵다 (가려졌거나 흔들렸다).
"배치를 못 구한 ID" 가 나오면 그 마커가 다른 마커와 한 장에 같이 찍힌 적이 없는 것이다.

### 자로 재는 방법 (예비)

사진 측정이 안 될 때만. `markers_W.json` 에 `{"center": [x, y, z], "up": "+Y"}` 형식으로 넣는다
(마커를 판 변과 나란히 붙였을 때 — `pose.load_layout` 이 두 형식을 다 읽는다). 자 오차가 최종 오차로 1:1 전달된다.

## 6. 3D 맵 촬영 — 마커를 붙인 채로

기존 수집본(`aerover/sessions/20260919_*`)에는 마커가 없다. **마커를 붙인 뒤 새로 찍는다.**

- **aerover 로 찍는다.** [드론 상태] → [연결] → 수집 제어. 갠트리를 **한 바퀴 이상** 돌린다.

- 궤도가 360° 라 모든 마커가 수십 장에 찍힌다 — 삼각측량에 필요한 "마커당 3~4장" 은 자동으로 넘는다.

## 7. 드론 카메라 캘리브레이션 (체스보드)

solvePnP 는 카메라 내부 파라미터(초점거리 · 주점 · 왜곡)를 **반드시** 요구한다.

`aerover/cameras_imx477_6mm.json` 이 있지만 **ODM 번들조정이 수렴한 값이지 캘리브레이션이 아니다**
(`aerover/src/config.py` 주석). 왜곡 k1 = -0.46 인 강한 광각이라, 실시간 자세 정확도를 믿으려면 직접 잰다.

### 절차

1. **`chessboard.pdf` 인쇄** (A4 **가로**, 배율 100%). 1쪽 눈금자로 확인 → **사각 10칸을 한 번에 재서 10으로 나눈다.**
2. 평평한 판에 붙인다.
3. **드론 카메라로, 스트리밍 경로 그대로** 15~25장.
   - ⚠ **반드시 1280×960** — 스트림 해상도와 같아야 한다. `raw_size (2028,1520)` 풀센서 모드도 그대로 (다른 센서 모드는 화각이 잘린다).
   - **갠트리 위치에서 찍지 말고 카메라 앞 30~60cm 에 들고** 찍는다. 1.5m 거리면 보드가 약 190px 로 작아 가장자리 왜곡을 못 잡는다.
   - 체스보드가 화면 **가장자리 · 네 모서리**에도 오게. 왜곡계수는 가장자리에서 나온다.
     **맨 구석까지** 보드 코너가 닿아야 한다 — 가까이 들면 보드가 커서 구석에 못 닿으니,
     일부는 **조금 멀리(작게)** 들고 네 구석에 하나씩 밀어 넣는다. `calibrate.py` 의 "구석 도달" 이 90% 미만이면 더 찍는다.
   - 기울기를 다양하게 (정면만 찍으면 초점거리와 거리가 분리되지 않는다).
   - aerover 수집 기능으로 찍으면 원본 JPEG 가 `sessions/<회차>/` 에 그대로 남는다.
4. 계산 (직접 돌려도 되고 폴더만 넘겨줘도 된다):
   ```bash
   cd apps/aruco
   uv run python calibrate.py ../aerover/sessions/<회차> --square <1번에서 잰 mm> --preview undist.jpg
   ```
   - 판정 5개(재투영 RMS · 장수 · 가장자리 커버 · 구석 도달 · 해상도)가 전부 **통과**면 끝. 결과는 `camera_1280x960.json`.
   - "장별 재투영 오차" 에서 혼자 튀는 장(흔들림 · 반사)은 폴더에서 지우고 다시 돌린다.
   - `undist.jpg` 에서 체스보드 선이 **곧게** 펴졌는지 눈으로 본다.

> **드론을 갠트리에 고정한 뒤 카메라를 다시 만지지 않는다.** 초점 링이 돌면 캘리브레이션이 무효다.

## 9. 다 되면 넘길 것

1. 인쇄된 마커의 실제 한 변 길이
2. 줄자로 잰 마커 중심 간 거리 (최소 0↔2, 가능하면 0↔6 · 2↔4 · 대각선)
3. **가까이 찍은 회차** (배치 측정용, 5절) — 마커를 새로 붙이거나 다시 붙였을 때마다
4. **ODM 회차** (400~500장 수집 → ①~③) — 3D 맵 정합용. 같은 사진이 라벨링 데이터도 된다

## 10. 흔한 실패

| 증상 | 원인 |
|---|---|
| 마커가 거의 검출 안 됨 | **흰 여백을 잘라냄** (09-22 실제로 겪음) / 광택지 반사 / 종이가 말림 / 소품이 일부 가림 |

| 시연 때만 안 맞음 | 촬영 후 마커가 움직였다 / 다른 자리에 다시 붙였다 |
